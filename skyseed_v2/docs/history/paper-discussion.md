## Extensibility：用户确定的贡献方向

### 核心表述与研究者视角

以下按目标能力全部完成后的价值概括，用于表达论文希望达到的贡献；实际状态在对应功能项标注。

Skyseed 提供一个便于定制和扩展的卫星互联网仿真框架，通过 PhysicalWorld、Planner、Compiler、Runner 的清晰职责划分，以及可配置、可替换、可组合的 Model 和后端扩展入口，让研究者将改动集中在自己的研究问题上。研究预计算路由时，可以替换 Route Model，并复用既有组网与执行流程；研究路由与连接的联合设计时，可以在明确的连接选择和路由规划职责内组合相应 Model；采用 OSPF 等实际路由协议时，可以选择对应模式，让协议在运行中决定路径；部署应用时，可以按卫星、GS 等节点类型或范围统一配置内置服务或用户程序。框架负责承接这些扩展所需的物理建模、连接生命周期、编译、运行与观测等公共工作，使研究者能够清楚判断需要改什么、如何接入，以及其余部分如何继续配合。

核心理解：**让研究者的改动范围与研究问题相匹配，并由框架承接其余工作。** 判断 extensibility 的重点是插件或替换入口是否方便、跨模块责任是否清楚、多个扩展能否协同，以及未替换的部分能否继续支撑实验。沿流程说明各 Model 的网络职责、输入输出和替换效果，是解释这种便利性的依据。

用户已认可本节作为初步讨论素材，2026-09-11 暂告一段落，有需要再补充，仍不制作 PPT。以下是论述层次，不增加代码架构层或新组件：

| 展示层次 | 要回答的问题 | 内容范围 |
| --- | --- | --- |
| 1. 框架设计理念 | 为什么能够把研究改动与底层执行分开？ | PhysicalWorld／物理建模、Planner、Compiler、Runner 四个职责，物理与规划语义和具体后端解耦 |
| 2. 具体可扩展能力 | 研究者可以替换、组合或增加什么？ | Model 配置／算法替换／组合与跨 Shell；后端适配或替换、实际 OSPF、内置和自定义程序服务 |
| 3. 面向研究者的使用入口 | 如何方便地配置场景、接入扩展并运行？ | Python 场景描述，emu／simu／main 分工；Model 接口、参考实现与自定义实现的装配；未来通用轨道数据导入；面向实际使用的 Agent 辅助文档、skill 与 tool |

统一接口和参考实现是 Model 替换机制，其示例／文档／接入步骤同时支撑第三层使用体验，展示时不重复计为两项独立创新。实现状态逐项附注；GS 与地面网络衔接暂不纳入，其他论文方向及竞品比较不主导本部分。

| 研究需求／功能类别 | 期望的扩展范围 | 当前状态与完善方向 |
| --- | --- | --- |
| Model：只研究预计算路由 | 替换 Route Model，在既有运行连接图上求路，复用物理、组网及现有 BPF 编译／执行 | 已实现接口与实例注入；第三方扩展示例、文档和使用体验待优化。这里的 MPLS-like 是有限类比 |
| Model：路由指导连接或联合设计 | 组合相关 Connection Model 与 Route Model，职责分别落在连接选择和路径规划 | 两类接口已实现；组合式扩展的输入、共享决策和调用关系待完善，尚未验证任意联合算法都能直接插入。不能仅凭两个可替换接口就声称完成双向协同 |
| 后端：实际路由协议 | 选择 OSPF 模式及相关配置，由框架接通相应执行支持 | Skyseed 动态卫星 OSPF 模式未实现；复用 SEED 能力并完成节点、动态接口与后端适配 |
| 路由语义／后端：IPv6 与途经点约束 | 支持 IPv6；除完整路径外，也能描述有序途经点，由兼容机制实现段间转发，SRv6 作为参考方案 | 未实现；需完善路径意图表达、地址与转发支持及模式兼容关系，不是给当前 IPv4 Route Model 增加一个参数即可完成 |
| 后端：节点应用与服务 | 按节点类型或范围统一安装内置服务、脚本或程序；用户暂称 payload layer | 统一入口未实现；需完善批量目标选择和程序装配，名称与 API 尚未确定 |

组合扩展仍须明确各方交换的信息与决策顺序；职责清楚不表示模块之间没有必要联系。框架的目标是把这些联系表达成明确、可复用的接口，减少研究者自行贯穿前后端接线的负担。具体待完善点留在下文，不在核心介绍中展开实现细节。

### 覆盖范围与现状边界

用户要求包含后续能力：实际 OSPF 路由及相应 Compiler／Runner 支持、跨 Shell 通信，以及按注册节点类型或范围统一安装内置／用户自定义程序服务。用户同时要求核对目前 Model 的替换机制并完善扩展体验。具体采用新后端组合还是内部适配、OSPF 配置是否由扩展后的 Route 角色表达，仍待讨论。

建议用于论证的精确范围是：在约定输入、输出与生命周期内替换算法，复用未受影响的框架层；新物理事实或运行中产生路由等新语义，可能需要先扩展相应合同。不能将“已有接口”写成任意新研究都只需改一个参数。框架复用也不保证第三方算法继承参考 Model 私有的求解优化或相同运行性能。

### 框架设计：物理／规划语义与执行后端解耦

用户确认前后端分离属于 extensibility，并将其定位为高于单个 Model 的整个 framework 设计理念，需要解释四个大组件分别对应什么。PhysicalWorld／Planner 表达位置、可行性、连接选择、链路参数及路由等网络语义；Compiler 将已决定的语义转换为具体后端意图；Runner 在实际环境中执行。研究者替换上层算法时，可以复用兼容后端；扩展执行后端时，可以复用其能够承接的上层语义与 Models。

| 组件／职责范围 | 核心问题 | 提供给后续阶段的内容 |
| --- | --- | --- |
| PhysicalWorld 与物理 Models（用户所说 topology／physical world） | 网络实体在哪里、具有什么能力、哪些连接在物理上可行？ | 物理状态、候选连接及相关物理属性；实际运行拓扑还需 Planner 选择 |
| Planner | 在物理条件和研究策略下，网络应怎样运行？ | 连接选择与生命周期、服务关系、有效链路参数及当前预计算模式的路径等规划结果，通过 Plan 交付 |
| Compiler | 如何把规划结果转为特定后端的执行意图？ | 后端所需配置和操作表达，保留规划时序与依赖，不重新做研究算法决策 |
| Runner | 如何在实际环境中按时实现这些意图？ | 实际连接、参数及转发状态和执行证据 |

物理候选、规划决定、编译意图和实际状态保持各自含义；这种分离既支持扩展，也为其他方向提供基础，但当前只展开其对扩展范围与框架复用的价值。

**已实现：** 物理／规划层与 BPF 编译、执行层的职责边界，及通过 Plan 传递规划语义的现有执行链。这里的独立性针对具体容器操作、BPF 表项和实际接口绑定等后端细节；Emulator 构造仍复用 SEED 实体，不能扩大为整个框架与 SEED 无关。

**待优化／未实现：** 通用后端扩展入口与兼容能力表达有待完善，第二套可切换执行后端尚未实现和验证。OSPF 等模式改变路径产生的位置与时机，还需扩展相应语义，不能承诺任意新后端都能在完全不改上层的情况下接入。这些状态在后端类别中展开，不将“前后端分离”另算成与后端替换无关的独立贡献。

### 场景构建与输入

用户认可将场景构造便利性纳入 extensibility：熟悉网络但不擅长大型程序开发的研究者，也能沿明确的 Python 构造流程描述所需网络、组件和参数，主要关注实验网络本身。它作为 extensibility 的使用入口和支撑设计，可称为“面向网络研究的场景构建与配置”；易用性是其直接效果，不单独增加第五条论文贡献。使用已有组件配置场景，与编写全新算法所需的开发工作应分别说明。

当前源码事实：`emu` 构造静态网络实体及关系，容器是后续编译部署的实现；`simu` 配置时间、物理假设和规划 Models；`main` 组织生成、交付等流程。现有场景也可读取项目格式的 shell、GS、Zone 等配置文件，因此不能把“外部标准轨道数据未接入”写成“没有文件导入”。

- **已实现：** Python 实体／组件装配入口，项目格式配置加载，以及 emu／simu／main 的基本职责分工。
- **待优化：** 让 Example 更集中地展示网络配置、Model 选择和有意义的流程；当前 main 仍含较多通用生成、封装和工具编排细节。支持职责整合为既有候选方向，不在本轮执行入口重构，也不将“非专业程序员容易使用”记为已验证结论。
- **未实现：** 通用外部轨道描述数据的导入与适配。具体格式和入口待讨论；解析数据之后还须配套轨道位置计算、时间／坐标解释及接触预测，不能仅替换文件读取就认为完整支持。

#### Agent 辅助的场景构建与实验使用

用户新增目标：提供面向 AI Agent 的使用文档、skill 和可调用工具，使研究者能通过描述需求，快速构建或修改卫星网络 Example、选择配置组件并使用 Skyseed。这里的 Agent 服务于终端用户使用框架，不承担核心仓库开发，也不是卫星内运行的 AI 路由／控制 Model。本轮仅讨论设计，不创建或安装 skill、实现工具或调度 Agent。

定位：extensibility 的第三层“面向研究者的使用入口”。框架已经具备的明确职责、配置与装配入口、自定义组件合同、分阶段产物和检查／观测资料，是未来 Agent 可靠使用框架的基础。AI 辅助开发经历可以作为设计经验来源，论文价值应落在用户能否更容易准确地完成任务，不将开发方式本身记为扩展能力或效果证据。

**状态：专门面向用户的 Agent 支持未实现，已有可复用基础。** 当前有 Examples、user-guides、面向维护的 codex-reference、配置校验及生成／运行／离线分析入口；这些不等于已提供用户 Agent skill、专门工具接口或已验证的自动化使用流程。待完善方向包括适合使用者阅读的能力说明、清晰的操作入口、便于程序读取的结果和错误，以及小型任务示例。

| 候选 skill 工作流程 | 教给 Agent 的任务方法 | 预期交付 |
| --- | --- | --- |
| 构建／修改场景 | 将研究需求映射到星座、GS、能力、时间和模型配置，按 Example 流程装配 | 可编辑的 Example／配置，以及关键选择和假设的摘要 |

| 生成实验与理解结果 | 使用现有生成／执行入口，读取对应阶段产物，解释配置问题和已记录结果 | 产物位置、运行状态及有依据的解释；不能从配置合法推断实验已正确运行 |

| --- | --- | --- |

这些 Agent 可调用能力应使用既有配置、生成、运行与 Tools 的职责和入口；新增所需公共入口另行设计，不依赖私有函数作为长期接口，不另造一套物理／规划／执行逻辑。Agent 操作工具与仓库现有离线检查 Tools 的职责不同，不能让后者顺带接管生成或 Runner。

Agent 阅读材料重点是“如何使用当前版本”：可用 Model 与参数、输入输出和单位、最小 Example、常用改动示例、能力组合条件和错误解释。可复用现有文档事实，但不直接把维护者架构治理文档当成用户操作指南；不维护一套与正式接口脱节的能力定义。

展示示例（未来使用流程，非已完成演示）：用户要求“基于已有示例构建双 Shell 网络，读取给定 GS 配置，每星最多四条 ISL，模拟十分钟，先生成网络配置和规划结果”。Agent 查询当前能力、完成配置与装配、核对并返回网络摘要，再调用生成入口并给出规划产物。若请求超出当前版本能力，如要求尚未支持的跨 Shell 链路，应指出缺口和相关扩展位置，不能编造一个参数并宣布已经支持。

待将来评估时，可用少量代表性使用任务检查配置是否准确、是否保持用户约束、出现错误后能否修正，以及人工介入和完成成本；这是候选证据方向，本轮不开展评估。文档可保留完整例子，PPT 可用“需求 → Agent 使用 skill／tools → Example／配置 → 既有框架 → 可检查结果”的流程图代替长段文字。

### Model 配置与替换

#### 替换机制与扩展体验

**已实现。** 角色合同主要采用 Python `typing.Protocol`，参考实现是独立的具体类。`Simulator.create_physical_world(...)` 与 `Simulator.create_planner(...)` 接收 Model 实例。第三方实现遵守方法、值类型及语义合同即可注入，不要求继承默认算法。当前 Example 直接展示构造与传入方式。既有测试源码包含非默认 ISL、GS、Zone、Route 与 Parameter 实现的注入／结果校验用例；这不是本轮重新测试或完整第三方扩展验证。

用户希望进一步理解其与 superclass 的区别，解释时分清三者：`RoutePlanningModel` 是方法、输入输出与行为的约定；`GatewayHopCountRoutePlanningModel` 是遵守约定的参考算法；研究者自己的类可以直接遵守同一约定，也可以按需要继承或复用其他实现。当前参考 Route 类本身不继承接口类。Planner 在构造时接收选定实例并调用其方法，继承关系不是接入的必要条件。

当前支持的使用方式包括：配置参考模型参数；传入独立的自定义实现；在实现内调用已有研究算法并适配其输入输出；按需要通过组合复用已有实现。继承参考类在合适场景下也可以使用，但默认实现的私有缓存／算法内部结构不因此成为稳定扩展接口。单独函数或外部算法的结果若不符合合同，仍需一个满足模型接口的适配实现。这里是构造时显式选择实例，不是已经具备插件文件自动发现、安装管理或运行时热替换。

比较 superclass 时区分“继承只有接口约定的基类”和“继承包含算法实现的默认类”。前者也能形成清晰的可扩展框架，Protocol 不是天然更优的论文创新；后者便于复用特定算法，但独立算法可能不需要其内部实现。Protocol 的实际便利是允许符合约定的现有类直接接入、减少强制继承关系，同时仍可选择显式继承。接口方法名称相同并不足够，参数、结果类型、变化记录及语义／生命周期也须兼容。源码中的 Route 接口要求 `plan_route_outcomes(...)` 和 `shutdown(...)`，返回 `RoutePlanningResult`，包含 outcomes 与 transitions。

可附带的理解示例：简化网络有 `A → B → D` 与 `A → C → E → D` 两条可行路径，研究者编写避开 B 的算法，在自定义 `MyRouteModel` 内接收现有连接并返回第二条路径及规定的变化记录；在 `simu` 创建 Planner 时，将 `route_model=GatewayHopCountRoutePlanningModel(...)` 改为 `route_model=MyRouteModel(...)`，其余兼容流程复用。`MyRouteModel` 可以不继承默认类，也可以内部调用已有求路函数。此处只说明接入方式，不表示该替代算法已经实现。代码示意应保留实际方法名与必要参数，并标明省略算法与其他装配参数。

**待优化：扩展契约与使用体验。** 建议维持“接口合同、参考实现、研究者实现”三者分离，按需提供可继承的便利基类，但不把默认算法本身作为所有研究的强制父类。补充最小自定义 Model 示例、配置与语义身份说明、契约检查和完整链路示例。这里是 Work 的建议，具体 API 未批准。

本轮找到的具体完善方向：

1. `PhysicalLinkModel` 的 Protocol 目前只要求 `compute_observation`，Producer 通过可选 `predict_contacts` 方法准备接触证明。内置证明路径只为确切的 `CircularOrbitPositionModel` 生成连续运动证明，其他 Position 实现留下 unknown。当前非零准备／最小服务准入需要这些证明，因此新的位置算法不保证单独替换后就保留原有完整效果。应明确位置与接触预测之间的可替换能力合同。
2. Planner 的候选搜索会读取默认 GS Model 的 `_search_hint`、容量缓存与搜索扩展方法，以及默认 ISL Model 的 `_configuration`。基础选路／选择入口已有，相关性能优化尚未完全通过对外合同表达。完善方向是使第三方模型不必仿造默认实现内部结构来使用搜索优化。
3. 参数、Zone 等现有接口只覆盖当前输入语义。负载反馈、可达性协同、任意物理几何等新研究须确认输入是否足够，不能一概声称只换算法即可。

### 后端替换与扩展

#### 多种路由语义与实现的选择

用户在 NetSatBench 调查后明确补充：方便替换不同路由协议／实现是 extensibility 的目标之一，未来考虑 IPv6 和“指定中间点，而不指定整条路径”的方式。后者在讨论中可称为“途经点约束路由”或“基于分段的路径控制”，SRv6 是具体参考；不把一般路径意图与某种协议等同。

预期既能指定完整逐跳路径，也能指定有序途经点，或由运行中的分布式协议选路，并允许合理组合。IPv4／IPv6 属于地址与网络层支持维度，不与预计算、分布式、途经点约束互斥；一项路径策略也不应天然绑定唯一的数据面实现。框架需要明确各模式的输入输出、决策范围及兼容条件，让其余阶段能够承接研究者的选择。

**已实现：** 当前完整路径结果及目的 IPv4 转发语义内的 Model 替换、BPF 编译执行。**未实现：** IPv6 正式执行链、途经点意图与实现、实际 IGP 模式和通用可切换组合。涉及新语义时可以扩展相应合同，但目标是形成可复用入口，避免每个研究者自行修改整条流程。具体模式、接口和默认选择仍待讨论；不自动修改既有架构。

#### 实际路由协议与 OSPF

状态：Skyseed 动态卫星网络中的 OSPF 模式未实现，适配方案待讨论；本地 SEED 已提供可复用的 Ospf／Routing 层。

当前 RoutePlanningModel 必须产出预定路径或明确不可达结果，BPF Compiler 降低既定结果，BpfRunner 实现它们。当前 BPF 数据面以目的 IPv4 地址查找逻辑出口并映射 live ifindex；论文宜称“预计算路由与 BPF 转发”，MPLS-like 可作有限类比，不表述为已经实现 MPLS 标签协议。

目标可以让用户选择 OSPF 模式并配置 router identity、接口参与、area／骨干与 ABR、cost、定时参数、GS 接入角色，以及 GS／Zone 服务前缀的通告与切换。实际邻居建立、LSA 传播、SPF 计算和路由安装由运行中的协议进程完成。

从语义上，应分开“框架规定网络何时变化”和“协议何时收敛”。Runner 完成连接变化不表示 OSPF 已收敛，后者应成为可观测结果。预期物理连通性可以供分析使用，不能伪装成已观测 OSPF 路径，未收敛也不能硬编码成现有的 planned-unreachable。

面向使用者的模式选择，与内部要改哪些实现是两件事。候选方案是配置选择兼容的协议执行和转发组合，复用物理、连接／参数规划及可共用的链路执行机制；不预先决定复制整个 Compiler／Runner，也不把有状态协议藏成当前 Route Model 的一个布尔开关。路由控制方式与转发后端是不同维度，并非天然一一对应。当前只有 BPF 后端，无通用后端替换 API。具体 Planner／Plan 扩展、配置所有权、后端接口和类划分尚未冻结。

用户进一步明确：启动并正确配置真实 OSPF 后，内部路径选择与更新交给协议，不由 Skyseed 逐路径控制；优先复用 SEED 已有协议能力。框架仍描述动态接口、地址、连接可用性与链路参数，使协议能够感知变化。接口 cost 或前缀通告策略若随场景变化，只更新对应配置，不直接决定 SPF 结果。

本轮核对本地 `/home/lionheart/workspace/seed-emulator`：`Ospf` 是依赖 `Routing` 的 Layer，现有 Routing 有 BIRD／FRR 配置路径。Ospf 默认处理注册类型 `rnode` 的节点及构建时所知接口，提供 AS／网络屏蔽与 passive/stub 控制。当前 Skyseed 卫星注册为 `extnode`，GS 注册为 `rnode`；普通 Service Binding 也只扫描 hnode/rnode/csnode，尚未包含 extnode。Skyseed 在装配地面互联路由层时会屏蔽 Skyseed AS 的 OSPF。因此应复用既有协议能力并适配节点选择与运行中创建的动态接口，不能把简单 addLayer 当成已接通卫星 OSPF。多 area 等需求也需核对默认模板以外的配置入口。这些结论针对本地 SEED checkout，不擅自归为所有上游版本行为。

以 FRR 为具体实现时，ospfd 处理 OSPF，Zebra 与 Linux 内核路由表交互，内核进行 IP 转发。若“ip table”指 IP 路由表，需要它；若指 `iptables` 命令，它负责过滤／NAT 等，不替代路由表。仍需接口／地址、转发开关及链路参数配置。GS 可以作为只配置上行路由的边缘端，也可参与 OSPF 等，角色和前缀通告策略须明确。BPF 转发不必启用，BPF 观测是否保留是独立决定。

这种模式减少框架预先求路的工作，却增加真实协议 CPU、报文和收敛成本。现有 BPF 运行规模与时序资格不能直接移作 OSPF 资格。

#### 按节点类型／范围安装 Service、Layer 与程序 payload

用户确定的目标：对某个注册节点类型或范围统一安装内置或用户自己的软件服务，可按卫星／GS、AS、Shell、Orbit 或指定节点集合等选择目标。程序 payload 指程序、依赖、配置、文件与启动方式，不能把已有 Satellite.payload 字符串元数据当成已经具备的程序安装系统。

状态：已有 SEED Node 的软件、文件和启动命令能力，Skyseed 节点继承这些基础；已有上游 Service／Layer／Registry 可供复用。面向 Skyseed 注册实体、按类型／范围批量安装并可组合的统一服务入口未实现。

本地 SEED Service 本身继承 Layer，通过虚拟服务节点与 Binding 安装到具体节点，支持服务间冲突检查；Filter 有 ASN、名称、IP／前缀与自定义条件。Registry 可按 scope/type 查询。但一个 Filter 匹配多个候选，不意味着对所有候选自动各装一份，普通 Binding 最终选一个目标；卫星 extnode 也尚未纳入其候选。需要完善目标选择与批量展开，复用已有安装能力。

用户体验示例可以是：给所有卫星安装路由程序；给一个 Shell 安装研究者的缓存或计算程序；给指定 GS 安装流量生成／服务端程序。OSPF 属于需要动态网络适配的协议类服务，普通应用 payload 可沿软件／配置／启动流程安装。具体公有 API、Service 与 Layer 适配方式未冻结，不引入新的运行所有者。

### 路由与转发机制

用户希望将目前称为 MPLS-like 的路由实现作为核心贡献之一：路径由前置计算产生，后端实现这些路径；并希望未来支持规划路径与局部感知／自适应结合，也能分别只选预计算或分布式模式。组合可能与尚未实现的 OSPF 后端一起设计，是否默认采用混合方式仍为候选。

#### 当前机制与术语

当前较准确的描述是“集中式预计算路由与计划驱动的转发更新”（centrally computed routing with scheduled forwarding updates）；可简称“预计算路由”。这是一项机制描述，不将其命名为新标准协议。

源码事实：Route Model 产生路径／不可达结果，Planner 发布 Plan，Compiler 将路径转为各节点转发意图，Runner 在正式时点落实。BPF 的每节点路由键为 node version 与目的 IPv4，值为逻辑出口，再映射实际 ifindex；没有在数据包中加入 MPLS 标签栈或执行标签交换。同一节点、同一目的的路径要求冲突出口时，当前 Compiler 会拒绝，不能据此声称具备不同 LSP／流的独立路径控制。

因此 MPLS-like 只能有限说明“控制路径计算与逐跳转发分工”的相似性；当前不具备 MPLS／SR 数据面协议保真度。预计算发生在仿真材料生成阶段，也不等于已实现真实网络的控制信息分发、PCE 交互、收敛或故障重算过程。是否需要进一步实现标签／分段等路径语义，要由论文要研究的行为决定，尚未批准。

状态：当前预计算路径与 BPF 转发执行链已实现；对外术语、可支持的路径语义及其适用 fidelity 范围待明确。路径规划和后端执行的具体贡献仍可论证，不能仅以“其他卫星仿真器没有预计算路由”立论。

用户进一步明确 BPF 的定位：它是当前高效落实和更新预计算路由的执行／优化机制，不是宣称实际卫星采用 BPF，也不需要借 MPLS-like 的名称证明其价值。论文可说明计划中的转发行为怎样被高效实现；BPF 本身不等于对某商用控制协议的复现，也不由此证明优于所有其他实现。预计算机制的行为保真与后端的执行效率分别说明，具体展示归属待讨论。

真实星座可能采用定制或组合机制，不能从内部实现未公开推导“卫星不使用标准 IP／IGP”。[RFC 9717](https://www.rfc-editor.org/rfc/rfc9717.html) 即提出 IS-IS、分段路由及卫星场景适配的组合；这是公开架构提案，不作为运营商部署事实。框架的多方案支持使研究者能够明确选择和更换研究假设。

#### 规划与局部自适应的组合

候选思路：利用可预测拓扑为正常运行规划路径或关键途经点；用局部感知和分布式机制处理意外链路变化或途经点之间的路径调整。实际 IGP 不限于 OSPF。需要明确规划与局部机制各控制哪些转发决定、什么时候允许偏离／恢复计划，以及实际变化如何被记录；不能仅并行启动两个转发机制就认为组合语义成立。

状态：OSPF 和混合能力均未实现；纯预计算、纯分布式、混合三种选择是用户提出的研究目标，默认模式和具体组合方式未定。现有 BPF 规模和时序资格不能直接当作混合协议资格。

[RFC 9717](https://www.rfc-editor.org/rfc/rfc9717.html#section-3) 的 SR-MPLS、IGP 局部适应与 [预期拓扑变化调度](https://www.rfc-editor.org/rfc/rfc9717.html#section-7) 为该方向提供技术依据。它是独立提交的 Informational 架构提案，不是 IETF 共识标准，也不是商用星座已部署证明。

### UT 接入、稳定身份与用户业务

用户确定为 fidelity 的第二条主要方向，**完整能力未实现**。用户明确纠正：**GZ 是 Ground Station（G）与 Zone（Z）的简称，标志卫星网络的两类通信端点，核心是 G→Z 与 Z→G；GZ 不是地理区域名称，也不是 Zone 的别名。** 现有需求构造及流量探测已区分这两个方向，Z 在卫星路径中由其服务卫星承接。Zone 服务与 G↔Z 端点路由为卫星段与具体 UT 的分离提供基础，但不等于已有 UT 注册、地址分配或会话保持实现。此前 Work 将 GZ 等同区域的解释有误，已纠正；本次不修改任何正式 API。

用户补充其设计动机：避免每个 UT 的接入、离开或接入位置变化都导致骨干逐用户路由重算。预期以 Zone／服务关系组织卫星段，把个体 UT 的接入和映射变化限制在相应接入职责内。这与 NetSatBench 将用户状态置于 SRv6 隧道端点的动机相近，机制不同：前者采用区域／服务抽象，后者采用端点隧道与基础设施路由分离；未来可以结合。区域抽象已存在，完整 UT 解耦机制尚未实现；服务星或骨干拓扑变化仍可能要求更新相关路径，不能扩大为所有移动性事件均无需改路。

预期每个需要实例化的 UT 可以独立承载用户软件与流量，覆盖以下语义：

- 注册／接入运营商，保留稳定的终端身份；
- 感知、选择与接入服务卫星；
- 获取并使用运营商提供的网络地址，表达身份、地址与当前接入位置的关系；
- 换星时更新接入与转发，研究会话连续性、中断、丢包及恢复行为；
- 使用独立容器执行实际用户应用，支持用户侧协议和业务研究。

稳定身份、地址保持、传输会话连续是不同问题，不由“容器名称不变”或“IP 不变”自动保证，也不把“稳定”直接写为无丢包、零中断。具体协议、状态和可验证行为后续讨论。[RFC 9717 §3](https://www.rfc-editor.org/rfc/rfc9717.html#section-3) 中终端地址与首跳卫星解耦的提议可供参考，不是现有 Skyseed 功能或某运营商的已证实完整实现。

Kubernetes 可作为大量 UT 部署、调度或重新部署的候选实现手段，尚未确定。fidelity 重点仍是 UT 的网络身份、接入状态和会话语义；部署位置或实例生命周期变化时，这些语义如何延续另需设计。大规模部署能力也涉及 scalability，但不提前替用户展开后者。

### 计算一：分层筛选与精确计算

**普遍问题。** 卫星与地面对象很多，但任一时点真正可能连接的对象只占一部分。对所有组合使用同样昂贵的精确几何判断会浪费计算。

**机制。** 先用成本低、不会排除合格对象的必要条件筛选，再对留下的候选做精确仰角、遮挡等计算。参考物理 Model 已有距离界筛选与后续精确资格判断。GS 查询中的候选扩展与轻量匹配可以作为关联材料，是否纳入同页待定；其候选搜索策略与物理保守筛选的完备性不能混用。

**成本表达。** 令 P 为潜在对象对数，Q 为通过粗筛的对数，c_s／c_e 为便宜判断／精确计算的单次成本。直接计算约为 P·c_e，分层方式约为 P·c_s＋Q·c_e。Q 远小于 P 且 c_s 远小于 c_e 时减少大量昂贵计算，但最坏情况下 Q 可接近 P，不据此声称渐近阶数必然降低。重点是保证粗筛不漏合格对象，让精确计算集中于合理范围。

状态：现有参考物理算法已实现。算法输入、过滤条件与最终精度应一并解释；内部数组 tile 和缓存不各自升级为核心贡献。

### 计算二：利用动态网络连续性的增量求解（保留）

用户从时空连续性理解这一方向。当前 GS 精确热启动主要利用时间连续性，即从上一时刻的可行分配开始求解下一时刻；路由的共同目的地与相关连通分量体现拓扑结构上的共享和局部依赖，不因几何上接近就假定结果接近。空间位置连续也不保证最优连接组合连续，算法仍需响应离散拓扑与容量变化。

**普遍问题。** 动态容量约束下的分配／匹配中，相邻时刻的输入往往有连续性；完全丢弃旧分配、从零求解，可能重复大量工作。

**方法特点。** 当前 GS 分配将仍合法的旧分配作为可行初解，在残量图上寻找并执行改善，直到满足当前五级整数目标的最优性条件。已有解只提供起点，允许通过交换重新分配，不以局部贪心或强行维持旧连接代替当前精确目标。特点应落在动态、容量约束、多级目标下如何继承可行状态并恢复最优性，而非泛称“缓存旧结果”。

**成本与质量。** 可以按“构图成本＋残量改善次数×每次搜索／修改成本”解释，不能直接声称最坏复杂度低于冷求解，或改善次数必与变化边数成比例。当前最优性针对实际候选图和五级目标；等目标解未必唯一。缺少可用初解时仍有冷求解路径。

解释性例子：每个 GS／卫星的容量均设为一。原来 GS1→A、GS2→B；之后 A 对 GS1 不可用，GS1 只能接 B，而 GS2 可以接 B 或 C。算法可以交换为 GS1→B、GS2→C，恢复两个 GS 的覆盖。这里是目标分配的求解过程，不是声称真实链路不经过准备便立即建立。

状态：已实现，用户确认保留该计算方向。表述应为“利用连续性减少重复求解工作，并保持当前候选图和目标下的精确最优性”，不写成牺牲少量准确性换速度。不能由继承旧解直接保证每个时刻净耗时都更低；收益幅度与最坏计算成本是另一问题，后续再结合已有证据说明。残量优化算法本身不声称原创。

#### 算法支撑：共同搜索与有条件的答案复用

这两项保留用于理解已有算法，不与精确热启动混称为同一种机制，也不因存在复杂度表达就自动升为独立贡献。

**同一时刻，多个请求共享搜索。** 同图上的多源同目的最短路可以从终点反向搜索。假设一千颗卫星都要到达同一 GS，一次反向 BFS 可给出各卫星到该 GS 的跳数，再为实际请求展开路径。当前实现按终点及一致的转发限制分组，并只展开需要的分支。令图有 V 个节点、E 条边，D 个请求涉及 K 个不同终点，仅图搜索部分的逐请求成本 O(D(V＋E)) 可变为 O(K(V＋E))；分组、路径构造和输出成本另计。一千为解释性假设。这说明利用共同子问题减少搜索次数，本身是成熟算法思路。

**相邻时刻，依赖未变时复用答案。** 若请求涉及的完整卫星连通分量和 GS 接入没有变化，另一不相关分量的链路变化不要求重算这条路。当前缓存以相关分量完整结构和 GS 接入为依赖，而非仅检查旧路径是否存在；新增更短路径也会使相应依赖失效。仍有依赖检测和图结构扫描／比较成本，不能写成零检查或总成本必然 O(变化量)。相关分量普遍变化时收益会下降。状态：上述两项均已实现。

### 运行一：基于 BPF 的转发状态准备与生效分离

**普遍问题。** 大规模动态网络中，大量预计算转发规则需要在目标时刻生效。如果到点才构造并逐条安装，正式更新的开销会随规则数增长，影响仿真器及时落实网络状态。

**方法特点。** 一套设计包含两个相互配合的部分：准备机制提前装载、构造并预写已知计划的转发状态；BPF 让未来版本已写入但尚未被选用，并在目标时刻通过活动版本选择器使其生效。这里将“状态已经准备好”与“网络开始使用该状态”分离。准备机制负责移出可提前完成的工作，BPF 提供直接切换已准备转发语义的机制，不把二者凑成互不相关的多项贡献。

当前 BPF 转发程序读取活动 generation 及节点内容版本，再查目的 IPv4 对应的逻辑出口并转发。目标时点更新共享的 active_generation 选择新版本。逻辑接口／live binding 分离使路由材料可以先于未来实际接口准备；按节点内容版本复用支持未变化内容的共享。这些是核心设计的配套机制，不各自扩成独立贡献。

**统一准备职责。** 首批与后继批次的装载、构造和预写，本质上属于同一材料准备职责，区别是触发时机。论文主线呈现“统一准备 → 待生效状态 → 到点切换”的关系，不以目前 Preparation／Maintenance 的代码分配定义两套设计。用户提出首批 BPF 写入也可统一交由 Maintenance 所代表的准备职责承担，以保持分工清楚；具体阶段命名、初始化与准备入口怎样整理留待后续实现设计，当前未批准修改。现状仅在本节末尾的实现对照备忘保留。

**成本表达。** 对 R 条规则，准备阶段仍需处理相应材料；已准备转发语义的发布子步骤变为一次选择器更新。关注从到点关键路径移出了哪些构造／预写工作，区别总工作量与到点开销。物理接口创建／删除、绑定和参数更新仍有各自成本，不能称整个网络更新 O(1)，也不由此推导跨跳数据包始终使用同一版本。

**保留被仿真网络的时间语义。** Preparation 减少仿真器自身的执行开销，不取消卫星网络模型要求的链路准备、控制消息传递或协议收敛等延迟。原则是按模型决定的时刻生效：例如某项操作从模型时刻 t 开始，模型规定经过 δ 才可用，即使仿真器已提前准备材料，也应到 t＋δ 才允许相应状态生效。真实协议实验中的交互和收敛过程仍由所选协议在被仿真网络中发生，不能用提前预写代替。不可预测事件只能在相关信息可用后准备，不以未来信息改变网络内部决策。

当前连接策略已经表达准备时长及从准备到可运行的状态转换。更通用的控制面延迟模型、真实 OSPF／其他协议收敛实验尚未实现，属于相应 Model／协议及后端扩展方向；不能写成所有延迟现在都有现成开关。Runner 的 Preparation 与被建模链路的准备时长是不同层面的概念，展示时必须分清。

状态：当前预计算路径的 BPF 与 Preparation 机制已实现。有限批次如何交付属于 fidelity 的更新组织语义；对已知计划如何高效准备与执行属于本节。其他协议／数据面仍按 extensibility 的选择与替换目标讨论，不将当前优化泛化成所有后端都已有同样机制。

### 运行二：减少重复控制与管理开销

**普遍问题。** 大规模仿真包含大量同类节点、连接和连续更新。逐对象、逐动作、逐时刻独立管理，会反复承担命令解析、执行环境定位、管理交互、用户态／内核边界往返及调度等附加成本。即使单次成本很小，随着对象数和更新频率增长也会变得显著。这个问题贯穿容器部署、连接生命周期和参数变化，不只属于路由或链路的一种操作。

**设计理念。** 以更少的控制操作驱动大规模网络：让可共享的管理工作在整体或批次范围内完成，让相关操作以完整语义一次表达，让执行端能够自行完成的后续工作随计划一并交付，减少重复控制和中间环节。目标是降低控制次数和每次控制的额外成本，而不仅是把单条命令执行得更快。

**同一理念的具体落点。** 以下用于解释设计共性，不拆成多个平行贡献：

| 场景 | 设计表达 | 减少的重复成本 |
| --- | --- | --- |
| 容器部署与整体管理 | 将可共享的准备、查询和管理按整个部署或批次组织 | 每个容器重复发起外围管理流程及交互 |
| 连接创建与配置 | 直接面向目标 namespace 提交完整连接操作，合并能够同时表达的属性 | 中间命令层、反复定位执行环境、创建后逐项配置 |
| 大量同类网络操作 | 根据真实依赖合并提交，复用共同控制上下文 | 多次调用、上下文切换和可避免的控制边界往返 |
| 链路参数随时间变化 | 将已知时间表或 Model 时间函数交给执行端，由内核按时间使用 | 控制器逐链路、逐时点反复重配置 |

容器部署补充已定位到已有记录：采用 cgroupfs 让 Docker/runc 直接管理容器 cgroup，减少逐容器 systemd transient scope 的管理交互；容器自身的 cgroup 和隔离仍然存在。它是采用的宿主运行配置，可说明削减外围管理成本，不作为自研算法或 Docker 已合并全部容器内部注册的说法。具体资料见下方实例库。

**成本表达。** 可以将执行成本区分为必要网络工作与附加控制工作；后者取决于控制调用次数及每次的管理、交互成本。本方向通过共享、合并和将计划交给执行端来减少这两项。按批次组织不会自动消除每个对象必需的内核工作，提前交付时间表也仍需消费事件；这不影响以控制开销削减作为统一设计方向。后续证据应围绕减少了哪些重复流程、调用和往返，再说明其时间收益，不把全部加速归因于用户态／内核切换。

**实现状态作为附注。** 直接 Netlink／BPF 控制、namespace 通道持有和 veth 创建属性合并已有实例；容器部署已有优化素材，具体例子后续选择；qdisc 参数时间表及连续函数的内核执行未实现。现状用于说明覆盖程度与待完善位置，不限制上述设计目标。参数时间表可以按已知计划分批续入；具体内核机制、时钟和队列参数语义在后续设计中确定。

运行一主要减少生效关键路径上的工作，运行二主要减少完成同样网络工作所需的重复控制开销。两者可由同一个机制同时支持，叙事区分关注点，证据不重复计算收益。

**C. **D. 依据实际拓扑依赖确定路由重算范围。** 将请求依赖表示为相关完整 ISL 连通分量及对应 GS 接入；无关接入或其他分量变化不触发该请求重算，相关分量新增捷径、分裂或合并则会失效。重算请求再按同终点共享反向 BFS。特点是把动态网络的关联范围用于求解决策，不能只说“缓存路径”。状态：已实现／待优化。现有依赖仍可能扫描整张图，分量内变化也可能使较多请求失效；待优化方向是减少依赖更新成本、研究更细的有效性证明与影响范围，同时保留最短路语义。来源：路由依赖与分组（历史源路径：`../../src/skyseed_v2/simulator/_route_computation.py`）。作为辅助实例，不独立扩大贡献数量。

**E. 利用轨道规律与运动边界证明连续接触区间。** 对符合圆轨道条件的 ISL，以全相位距离上界和保守视线条件一次证明稳定可用；其他链路按区间中点与运动位移上界，证明整个区间而不只判断离散端点。它同时体现时间连续性利用和分层证明。若 P 对链路中有 S 对可作全相位证明，T 个区间的 ISL 资格判定可由逐对逐区间的工作减少为一次证明加对其余链路的区间判定；位置生成与地面查询成本另计。状态：当前圆轨道路径已实现／待扩展。待优化方向是让其他轨道或导入位置模型提供有效的运动边界、改善保守界过宽导致的 unknown 区间；无法证明不表示不可用。来源：连续接触预测（历史源路径：`../../src/skyseed_v2/simulator/models/_contact_prediction.py`）。可作为两组共用的补充例页，不重复算作两项贡献。

#### 运行一的实例：未来路由可准备，实际链路可按时建立

用“稳定逻辑端口 → 当前实际接口”的映射承接 BPF 版本切换：未来 veth 尚未创建时，未来转发状态即可按逻辑端口写好；到规定时刻建立实际连接、关联接口，再选择已准备版本。这样把准备状态与物理连接寿命解耦，是支撑提前准备理念的代表机制。状态：已实现；首批／后继准备的入口与职责统一作为待整理方向，具体实现另议。来源：[BPF 表与生命周期](../../src/skyseed_v2/backend/bpf/runner/README.md)。例页以未来版本准备、逻辑端口、实际接口和活动选择器的关系为主，不展开私有表名清单。

#### 运行二的主实例：直接控制 namespace 中的仿真链路

把下列过程组织成一个代表实例，而非拆成“少启动一个进程”等琐碎项：

1. 动态网络节点可采用 `network_mode: none` 启动；仿真链路由连接两侧 namespace 的 veth pair 直接承担，不为每条动态链路引入 Docker network 和 Linux bridge 的管理生命周期。此范围指 Runner 创建的动态链路，静态地面网络按其自身需求保留。
2. 主机侧控制器持有明确的 namespace 目标及对应 Netlink 通道，直接执行网络变更；正式 Main 无需为每个动作经过 docker exec／nsenter／shell，再在容器内启动 ip／tc。减少的是整条跨容器执行和命令控制路径的反复成本。
3. 用一次 veth 创建请求同时表达两端 namespace 与可合并属性；用 Netlink 直接配置内核 qdisc、地址、邻居和必要路由，用 BPF 接口准备及切换转发状态。保留内核真实设备和排队处理，减少外围工具及分散配置往返。

上述部分均已实现。所体现的设计是：让控制器直接表达网络变化，按实际连接语义组织底层操作，减少容器管理层与命令工具层对每次动态更新的介入。来源：无静态接口节点的部署（历史源路径：`../../src/skyseed_v2/compose/launcher.py`）、[namespace 控制通道](../../src/skyseed_v2/backend/bpf/runner/privileged_runtime_command.py)、[直接内核操作](../../src/skyseed_v2/backend/bpf/runner/kernel_netlink.py)。这些是运行第二项的首选代表，不把“减少 docker exec”降格为普通去重，也不声称所有 Linux networking 组件均已移除。

**同一理念的未来延伸。** qdisc 参数序列／函数随已知计划交付给内核，执行端按时间应用，进一步减少控制器逐时刻跨边界重配置。状态：未实现。它与现有直接 Netlink 控制分别说明减少单次控制路径、减少控制发生次数；按已知批次补充时间表、连续参数语义与执行机制留待后续设计。

**部署侧补充实例。** 已采用 cgroupfs，由 Docker/runc 管理容器 cgroup，减少逐容器 systemd scope 创建与协调。它体现减少外围管理层交互，作为宿主配置实例简述即可；不与前述 namespace 网络控制合并为同一实现，也不声称单项加速倍数。来源：[H3 历史决定](../history/optimization-decision-history.md#h3)。镜像去重、普通缓存和零散清理不作为本轮首选例子。

### 一、最终网络的高级可视化

### 二、中间过程的可观测与可解释（核心）

**设计理念。** 以阶段输入、Model 作用、阶段输出和状态变化串联观察路径，使研究者能够沿同一时间与对象追踪网络如何形成。既展示最后选中了什么，也展示它来自怎样的候选、约束和记录的决策过程。以通用的阶段语义支撑基础视图，再容纳不同 Model 自己需要展示的指标和解释材料。

可按以下问题组织内容，而不以现有 Tool 文件清单作为主体：

- 物理设置产生了哪些可行连接和候选范围？
- 连接 Model 从候选中选择了哪些关系，哪些正在准备，哪些已经可用？
- 参数和路由 Model 如何改变链路属性、路径与可达性？
- 这些结果如何进入计划、编译及执行，最终实际运行与计划有什么对应关系？

**可解释性的来源。** 使用明确的输入／输出关系、真实记录的约束、选择或排除理由，以及前后状态变化帮助研究者理解决策。通用阶段输出可解释“该步骤产生了什么变化”；某算法更深的“为什么这样选择”需要它提供相应决策材料。可视化或 Agent 不从结果形状猜测未记录的内部理由，模型比较也不自动等同于已经完成因果实验。

**可扩展的观察能力。** 用户替换 Model 后，阶段结果应继续进入共同的观察链；模型特有的评分、候选排序、限制条件或决策轨迹，应有清楚、便于接入的展示方式。目标是研究者能够看见自己修改的部分如何影响网络，而不需要重写整套观察工具。具体记录形式、展示扩展接口和组件合同留待后续设计，不在本轮固定。

状态：已有较完整的阶段记录与可视化实例，第三方 Model 的通用接入体验待优化。现有物理和 Planner Tools 读取已保存记录，不重新执行 Model；配置描述来自公开装配值，不以直接读取私有字段为既定方式。但部分视图具有轨内／循环邻轨关系、既定阶段或参考场景等专用展示，尚不能声称任意新 Model 的内部决策都自动完整显示。待优化方向是梳理通用视图与专用视图边界、明确额外解释材料的提供方式，并让自定义 Model 有容易遵循的可视化扩展入口。

### 三、Agent 辅助自定义 Model 的可视化（归入过程可观测的扩展支持）

**目标。** 让用户在替换或新增 Model 后，可以借助 Agent 快速补齐对应的过程展示和解释。这里的 Agent tool 是供 AI 调用的工具，与现有供研究者浏览的可视化 Tools 区分；skill 用于指导它按框架约定完成这项工作。

可提供以下配套能力作为未来方向，名称和接口尚未确定：

- **面向 Agent 的说明文档：**解释阶段输入／输出、对象和时间身份、已有记录、通用视图与可扩展位置，提供小型记录样例。
- **可视化接入 skill：**理解自定义 Model 希望展示的决策 → 对应已有和需补充的记录 → 复用视图或生成专用展示 → 核对显示内容与模型输出的对应关系。
- **供 Agent 调用的工具：**查询记录与展示约定、读取样例及字段结构、生成或接入可视化骨架、检查字段和时间／对象映射。具体功能只作职责设想，本轮不创建工具、skill 或新接口。

设计重点是让可观测性随模型扩展持续存在，而不仅是降低一次画图的成本。Agent 根据明确信息组织展示，缺少的解释信息应指出并由模型提供；不生成没有记录依据的决策原因。

状态：专门的 Agent 可视化辅助能力未实现；现有阶段记录、Tools 与文档可作为基础。它与 extensibility 中的 Agent 使用辅助互相衔接：前者关注构造和修改研究场景／Model，此处关注让扩展后的研究过程仍可观察、理解。不能将两处描述计为已经实现的两套 AI 系统。

### NetSatBench 独立调查与 SRv6

2026-09-11 用户要求单独了解该平台及其宣传重点，Skyseed 自身设计叙事保持独立。本次网络访问恢复，已读取论文和公开仓库文档／相关源码；仓库固定为 `32ccf79faf4a3d767c21d308150673d79666a33e`（2026-09-08），论文为 arXiv:2604.27854v1（2026-04-30）。当前仓库晚于论文，不假定二者实现完全一致；没有部署、运行或独立复现实验。

**执行范围。** [公开平台](https://github.com/mSvcBench/NetSatBench/tree/32ccf79faf4a3d767c21d308150673d79666a33e) 以卫星、网关、UT 容器组成多机网络。[sat-agent 源码](https://github.com/mSvcBench/NetSatBench/blob/32ccf79faf4a3d767c21d308150673d79666a33e/sat-container/sat-agent.py) 直接在节点内创建 VXLAN 接口，以 Linux tc 配置链路，调用路由插件；是真实逐节点转发网络。真实接口可用 tcpdump 抓包，论文也给出命令；不由此推导自动全量逐跳记录和跨层关联已经齐备。

**扩展与操作。** [物理生成文档](https://github.com/mSvcBench/NetSatBench/blob/32ccf79faf4a3d767c21d308150673d79666a33e/docs/starperf-integration.md) 复用并扩展 StarPerf，以插件选择 ISL、过滤地面候选连接、处理天线约束、计算速率／丢包，再导出场景与 epoch。[路由接口](https://github.com/mSvcBench/NetSatBench/blob/32ccf79faf4a3d767c21d308150673d79666a33e/docs/routing-interface.md) 为 init／link_add／link_del，明确路由插件不管理链路创建删除或事件时序；内置 FRR IS-IS IPv4／IPv6 与本地 IPv6 邻接转发。另有离线 oracle 生成内核路由命令，支持跳数／时延指标、备用下一跳和断链前提前换路。

[CLI](https://github.com/mSvcBench/NetSatBench/blob/32ccf79faf4a3d767c21d308150673d79666a33e/docs/utils.md) 支持逐节点或按类型复制用户文件、执行程序、收集文件和查询状态；这与我们未来的批量 payload 使用场景重叠，但不能直接等同于 SEED 完整 Service／Layer 生命周期。[执行流程](https://github.com/mSvcBench/NetSatBench/blob/32ccf79faf4a3d767c21d308150673d79666a33e/docs/control-commands.md) 包括资源／拓扑感知的节点放置、部署、epoch 回放和交互注入。Etcd 通知节点内 agent 落实更新；公开多机部署使用 Docker／SSH，不因资源调度类比 Kubernetes 就记为 K8s 实现。

**SRv6 的含义。** Segment Routing over IPv6 用 IPv6 SID 表达经过的节点或需执行的转发功能；例如隧道入口封装外层 IPv6 与 SRH，写入有序途经点，分段之间仍由 IPv6 路由决定具体逐跳路径，出口解封装。SID 列表不必列出全部卫星；它与底层路由如何计算是不同问题，可以结合 IGP 或预安装路由。依据 [RFC 8754](https://www.rfc-editor.org/rfc/rfc8754.html) 与 [RFC 8986](https://www.rfc-editor.org/rfc/rfc8986.html)。当前 Skyseed BPF 未携带 SID／MPLS 标签，不能称为同一数据面机制。

其 [UT／网关案例代码](https://github.com/mSvcBench/NetSatBench/tree/32ccf79faf4a3d767c21d308150673d79666a33e/test/handover) 通过 Linux seg6 配置隧道，并实现自定义注册、链路报告、心跳、切换命令及完成响应。论文逻辑下行途经序列为“网关 → 网关侧服务卫星 → 用户侧服务卫星 → UT”，中间卫星负责基础 IPv6 可达性；用户状态主要在隧道端点。切换由网关协调两侧服务卫星，更新隧道，存在短暂停流处理；不是承诺零中断，也不是完整商用鉴权／地址分配系统。案例的 hybrid 指预计算基础设施路由、本地接入路由与动态 SRv6 隧道三类分工，不能当成已经验证了我们所说的 IGP 局部故障自适应组合。

**作者目标与证据边界。** 论文强调分布式扩展、多层真实软件实验、插件扩展、声明式可复现与操作便利。报告在 10 台工作 VM（共 72 vCPU／72 GB）运行 588 卫星＋5 网关＋7 UT，部署 92 秒；实验以切换策略和 TCP 行为为主。该规模、硬件和计时口径不能与 Skyseed 既有单机大场景直接排名。参数化物理模型与自定义接入控制具有明确抽象范围，不能由“完整容器框架”推成完整真实无线系统。上述数字与目标来自[论文](https://arxiv.org/html/2604.27854v1)，效果尚未独立复现。

关于规模的补充核对：论文 IV-A 明说场景为该 SRv6 案例而简化，未解释选择 10 台 VM 的具体原因，也未提供单机承载上限或随工作机数量变化的扩展曲线。数百颗星足以支撑其协议案例，但 7 个 UT 不能证明大规模终端能力，现有实验也不足以证明大星座容量上限。10 台 VM 是部署配置，不是 600 容器必须使用的最小机器数；展示分布式可行性是该实验的效果，作者是否专为此选择配置尚无证据。

**与 Skyseed 的初步定位。** 不能再用“只有我们有预计算、插件、职责分离、真实软件或 UT 切换”作为区分。NetSatBench 的公开扩展中心是场景／epoch 文件、物理插件、节点路由事件与运行命令；Skyseed 当前以 PhysicalWorld → Planner → Plan → Compiler → Runner 的语义结果交接，以及规划／编译／实际状态关系组织框架。这是组织方式与研究入口的差异，尚非优越性证明。我们的细粒度 Model、连接生命周期、计划落实和证据关联可以按自己的问题继续说明；通用后端、真实 IGP、UT 和批量 payload 仍保留未实现状态。无需围绕对方重排当前论文主线。
