# Planner Design Skill

Use this guidance when work touches routing, MPLS planning, gateway/zone
egress policy, or planner interfaces.

## Goal

Define planners as replaceable policy modules that consume a stable
`TopologySnapshot` and emit a stable `RuntimeUpdatePlan`. Planner logic must
not leak into runtime agents or installers.

## Required Interface

Any planner design should define:

- planner name and version
- planner input schema
- planner output schema
- planner assumptions
- planner validation rules
- planner-reported errors or infeasible conditions

Minimum required interface direction:

- input: `TopologySnapshot`
- output: `RuntimeUpdatePlan`

## Required Input Contract

Planner work should state which `TopologySnapshot` fields are required, such
as:

- active nodes
- active links
- serving-satellite mappings
- gateway availability
- zone ownership
- unique active zone-serving satellite selection per slice
- policy metadata required for gateway or zone egress

If a planner needs extra metadata, add it to the snapshot contract explicitly
instead of pulling it from ad hoc controller state.

## Required Output Contract

Planner output should be a generic `RuntimeUpdatePlan` that can be consumed by
distribution and agent layers. The contract should make clear:

- plan identifier and version
- target time slice or snapshot
- node-local subplans
- install ordering constraints if any
- validation hints if any
- rollback or replacement semantics if any

The output must remain generic enough that a runtime agent can apply it without
understanding why the planner made those decisions.

Do not prematurely define planner output as two literal runtime tables. The
plan may instead contain whatever the chosen runtime installer needs, such as:

- ingress classification rules
- label allocation results
- `LFIB` entries
- route rules
- cleanup or replacement rules
- validation expectations

## Default G/Z MPLS Planner

Iteration 2 should treat the default planner as one replaceable module with the
following semantics:

- `G-table`
  - `G` means gateway egress
  - mainly for `UT`-to-Internet or `UT`-to-gateway-direction traffic
  - the `UT` side uses local destination or policy information to choose a
    gateway or gateway-egress class
  - the `UT` side applies the corresponding ingress label before sending into
    the satellite network
  - the MPLS core forwards the packet toward the selected gateway
- `Z-table`
  - `Z` means zone egress
  - mainly for return or network-to-`UT` traffic
  - destination `UT` or destination address is mapped to the `UT`'s zone
  - each zone has exactly one active responsible serving satellite per slice
  - traffic is planned toward that responsible satellite
  - the responsible satellite handles final delivery toward `UT` access or beam
    abstractions

Document the semantics, but do not make them mandatory for the platform.

Intermediate satellites should not need to understand high-level G/Z concepts.
They only need node-local MPLS forwarding state generated by the planner.

## Alternative Planner Support

Planner design must leave room for:

- another MPLS planner with different label policy
- an IP-routing planner
- future hybrid planners

If a design choice would block an IP planner later, call that out explicitly.

## Agent Boundary

- No planner logic inside the runtime agent.
- No gateway-selection reasoning inside the installer.
- No zone-ownership computation inside node-local execution.
- No assumption that intermediate satellites understand G/Z abstractions.

Agents execute node-local plans only.

## Validation Expectations

Each planner proposal should include:

- one example `TopologySnapshot`
- one example `RuntimeUpdatePlan`
- one infeasible-case example
- one statement of what remains planner-specific versus platform-generic
